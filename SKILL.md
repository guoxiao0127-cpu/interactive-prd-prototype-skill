# Interactive PRD Prototype

Build a prototype that is both operable and readable as a product specification. Treat the right-side rule panel as a core part of the prototype, not as a tooltip or temporary overlay.

## Workflow

1. Inspect the existing project before choosing a framework or component library. Preserve its current framework, visual language, routes, and page structure unless the user requests a redesign.
2. Identify interactive targets: primary and secondary buttons, table rows, fields, tabs, status labels, cards, links, menus, workflow nodes, uploads, and important read-only areas. For every operation, inventory the fields it reads, displays, derives, submits, or updates and trace each field to its actual data source.
3. Create stable semantic IDs for targets. Never bind rule content only to visible text, array index, or DOM position.
4. Add a dedicated application-shell-level right rule rail outside route components. It occupies the full viewport height, slides in from the right, and must remain mounted across route navigation. Reserve its width in the application layout and keep it visible above business dialogs and their masks. Clicking a target passively selects and highlights it while the original click, focus, selection, navigation, dialog, submission, and mutation behavior continues exactly once. Provide close and reopen controls, and make every rule-bound target able to reopen the closed rail without consuming the user's action.
5. Store rule content and page change records as structured data separate from page components. Use the schema and interaction requirements in [references/rule-panel-spec.md](references/rule-panel-spec.md).
6. Keep the rendered prototype strictly read-only. Make the product owner update rule source files through Codex and rebuild the static prototype.
7. Populate concrete business rules and operation-field data sources from the user's source material and inspected project code. Do not fill the panel with generic UI narration such as “click to submit,” and do not infer an undocumented source system or field mapping.
8. Verify representative interactions, source-driven rule rendering, target highlighting, responsive behavior, empty states, and long content.

## Product Rules

- Default desktop layout: reserve a full-height application rail at the browser's right edge. Match its width to the application's expanded primary navigation width; use 240 px when the project has no reusable navigation-width token.
- Anchor the rail from viewport top to bottom, outside individual page cards and route content. It must look like a permanent application region, not a floating card or popup.
- Animate opening and closing as a short right-side slide. Opening must shrink or offset the application content by the same width so the rail never covers the business page.
- Do not implement the rule panel as a modal, dialog, popover, overlay drawer, teleported surface, or masked layer.
- Keep the rule rail readable and interactive while business dialogs are open. Constrain dialog masks and dialog layout to the remaining business-content region when possible, and place the rule rail above their stacking layer so neither the dialog nor its mask covers the rules.
- Default PAD layout: preserve the dedicated right rail when sufficient width exists; otherwise provide an explicit compact review mode without turning it into a modal or masked drawer.
- Keep the panel open when the selected target changes. Do not require hovering.
- Preserve the rail's open/closed state and last selected rule while routes change, including list-to-detail, detail-to-edit, and workflow navigation. Route components may register a new rule set or select a page rule, but route unmounting must never destroy or reset the application-level rail.
- When a destination page has no rule binding yet, keep showing the last selected rule so navigation context is not lost. When destination rules exist, switch to its page-level rule or the clicked destination target without closing the rail.
- Allow the user to close the panel. Closing must remove target highlights and restore the business page to its original full-width layout without leaving a blank column, overlay, or reserved gap.
- Provide a lightweight, discoverable control to reopen the panel and restore the last selected target. Do not require a page refresh.
- When the panel is closed, clicking any rule-bound button, field, table action, status, link, card, or workflow node must both reopen the panel on that target and execute the target's original behavior in the same interaction.
- Treat rule selection as passive observation. Never call `preventDefault`, `stopPropagation`, or `stopImmediatePropagation`; never return `false`; never replace, delay, debounce, duplicate, or require a second click for the original action.
- Do not add transparent hit areas, wrappers, masks, overlays, or `pointer-events` rules that intercept business controls. Do not change disabled states, tab order, focus, keyboard activation, drag, selection, hover, double-click, context-menu, or touch behavior.
- When capture-phase observation is necessary to survive route unmounting or component propagation, use it only to synchronously update application-level rule state. The event must continue unchanged to the original target and handlers.
- Show the selected page, module, target type, and target name at the top.
- Organize rule details into concise sections: function purpose, trigger/entry, preconditions, business rules, processing rules, operation-field data sources, field/data rules, validations and messages, result/state changes, permissions, exceptions, and related functions.
- Keep “business rules” separate from UI steps. Record eligibility, status transitions, calculation, merge/split, ownership, upstream/downstream synchronization, and other domain constraints as testable statements.
- For every field read, displayed, derived, submitted, or updated by the selected operation, show its field name, source system, source object or API, source field, acquisition timing, transformation or mapping, and fallback behavior when known.
- Distinguish user input, route/context parameters, frontend-derived values, local static dictionaries, backend APIs, databases, and third-party systems. Do not label all fields generically as “接口返回”.
- Add a read-only “页面变更记录” card in the panel's remarks area for the current page. Each entry must show what changed, original content, new content, and one change type: “新增”, “删除”, or “修改”.
- Keep page change records page-scoped rather than duplicating them on every target rule. When the selected target changes within the same page, continue showing that page's change card; when the route changes, switch to the destination page's records.
- For “新增”, use an explicit empty-state marker such as “无（新增）” for original content. For “删除”, use “无（已删除）” for new content. For “修改”, require both original and new content. Preserve multiline text and field-level detail so developers can compare the change directly.
- Record only confirmed differences from the previous prototype or specification. If the baseline is unavailable, mark the original content “待确认” rather than guessing.
- Hide empty optional sections.
- Give every important rule a testable statement. Prefer “Only records in ‘Unarranged’ status can be confirmed” over “Check status.”
- Use the exact button names, field names, statuses, and error messages shown in the prototype.
- If source information is incomplete, mark the specific item as “待确认” and list the missing decision. Never invent a business rule silently.

## Rule Source and Ownership

- Use a repository-backed TypeScript or JSON module as the only rule source of truth.
- Keep rule content out of browser storage, runtime APIs, and page components.
- Allow only the product owner to change rules through Codex and rebuild the static prototype.
- Render the rule rail as read-only text that users can select and copy.
- Store a rule-set version and last-updated date in the source module and display both in the rail.
- Mark incomplete decisions explicitly as “待确认”.
- Mark unknown field sources, mappings, transformations, or refresh timing as “待确认”; never invent lineage to make the panel look complete.
- Keep page change records in the same repository-backed TypeScript or JSON source as the rules. They are read-only in the prototype and change only through Codex and rebuild.

## Implementation Boundaries

- Do not replace dense rules with tooltips, popovers, toast messages, or scattered annotations.
- Do not use a dialog or overlay drawer for the rule panel, even if the framework provides one by default.
- Do not hard-code long rule text inside each button component.
- Do not mount the rail inside a route page, tab pane, dialog, or other component that is destroyed during navigation.
- Do not provide runtime edit, save, cancel-edit, restore, import, export, or content-management controls.
- Do not use `localStorage`, session storage, IndexedDB, cookies, or a backend to persist rule edits.
- Do not change existing business behavior solely to demonstrate the rule panel.
- Do not alter handler order, arguments, return values, request counts, navigation destinations, dialog timing, form validation, or mutation semantics when binding rules.
- Do not imply that prototype viewers can modify rules.
- Do not make every decorative element selectable; cover elements whose behavior, data, or state matters to development or testing.

## Verification and Handoff

Test at minimum:

- Selecting three different target types updates the correct rule.
- No edit, save, restore, import, export, or other rule-mutation control is rendered.
- The displayed version and update date match the TypeScript or JSON source module.
- Representative operations display concrete business rules separately from processing steps.
- Every representative operation field has a traceable source entry, or an explicit “待确认” marker when its lineage cannot be established.
- The current page displays one “页面变更记录” card in the remarks area when change records exist, and hides the card rather than showing an empty shell when none exist.
- Each change entry displays a valid type badge and the four required values: what changed, original content, new content, and change type; add/delete empty sides use explicit empty-state text.
- Switching targets on the same page preserves the page change card; navigating to another page switches to that page's records without leaking entries from the previous route.
- Long rules scroll inside the panel without moving the business page unexpectedly.
- The rail width matches the expanded primary navigation width, occupies the full right side from top to bottom, and remains fully visible when a representative business dialog and mask are open.
- Selected-target highlighting is visible but does not obscure the original UI state.
- Keyboard focus and close/reopen behavior are usable.
- Closing restores the original page width and reopening restores the last selected rule without changing business state.
- With the panel closed, one click on representative primary, secondary, field, link, and row-action targets both reopens the correct rule and completes the original action exactly once.
- Verify normal mouse, keyboard, focus, selection, navigation, dialog, form, disabled-control, and touch interactions before and after rule binding; behavior must be equivalent except for the visible rail and target highlight.
- Verify no rule observer calls event-cancellation APIs and no rule-layer element sits above or captures pointer input from the business page.
- Existing routes and primary prototype flows still work.
- The rail remains open with the last selected rule after at least two representative route transitions; returning to a rule-enabled page continues rule selection without remount flicker or state reset.

Report the files changed, the rule source module, rule-set version, update date, field-source coverage, page change record coverage, and any “待确认” business decisions, data lineage, or change baseline.
